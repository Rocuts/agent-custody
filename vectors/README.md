# Test vectors

Generated by `tools/make_vectors.py` (deterministic; a test regenerates them and compares bytes).
All keys are derived from public strings and are NOT SECRET. All data is synthetic.

Each directory has a `case.json` with the verifier arguments and the expected exit code / layer states.
`pass-*` vectors MUST exit 0, `fail-*` vectors MUST exit 1. `pass-12` and `pass-13` document limits: they pass on purpose.

| vector | expectation | what it shows |
|---|---|---|
| `fail-01-altered-entry` | MUST FAIL | One field of entry 1 changed, entry_hash left as is. |
| `fail-02-altered-entry-rehashed` | MUST FAIL | Entry 1 altered AND its own hash recomputed; the next entry's prev_hash exposes it, and the checkpoint root differs. |
| `fail-03-full-rewrite-with-checkpoint` | MUST FAIL | The whole log is rewritten and re-chained consistently, but the earlier signed checkpoint no longer matches, and the approval is not signed by the pinned approver key. |
| `fail-04-reordered-entries` | MUST FAIL | Entries 2 and 3 swapped. |
| `fail-05-deleted-middle-entry` | MUST FAIL | Entry 2 removed from the middle. |
| `fail-06-truncated-vs-checkpoint` | MUST FAIL | Log cut to 3 entries; the signed checkpoint covers 5, so the truncation is detected. |
| `fail-07-checkpoint-foreign-key` | MUST FAIL | Checkpoint signed by a different key with a different name; the trusted key has no signature on it. |
| `fail-08-checkpoint-forged-keyid` | MUST FAIL | Attacker copies the trusted key name and key id but signs with its own key: the signature does not verify. |
| `fail-09-checkpoint-root-altered` | MUST FAIL | One bit of the checkpoint root flipped, original signature kept. |
| `fail-10-checkpoint-from-other-chain` | MUST FAIL | A genuinely signed checkpoint of ANOTHER chain, presented for this log. |
| `fail-11-transplanted-entry` | MUST FAIL | The last entry is replaced by a perfectly valid entry from a different chain. |
| `fail-12-executed-without-approval` | MUST FAIL | Self-consistent log that records an approval-required action executed with no human approval. All hashes are valid; the policy layer catches it. |
| `fail-13-approval-after-execution` | MUST FAIL | The approval is recorded AFTER the action ran. |
| `fail-14-executed-after-rejection` | MUST FAIL | The human rejected the action, it ran anyway. |
| `fail-15-executed-after-deny` | MUST FAIL | A policy decision recorded 'deny'; the action was executed anyway. |
| `fail-16-approval-expired` | MUST FAIL | Executed after the approval's expires_at (compared on the host's own clock). |
| `fail-17-approver-signature-invalid` | MUST FAIL | The approver signature has a flipped nibble (hashes are re-chained so only the signature layer fails). |
| `fail-18-approver-key-not-pinned-key` | MUST FAIL | Signature is valid, but under a different key than the one pinned for 'approver-1'. |
| `fail-19-approval-replayed-from-other-chain` | MUST FAIL | A signed approval lifted from another chain (subject re-pointed): the signature covers chain_id and subject, so it fails. |
| `fail-20-cross-provider-claim-false` | MUST FAIL | Claims cross_provider=true while every reviewer is from the author's provider. |
| `fail-21-unknown-entry-version` | MUST FAIL | Entries declare v=2. A v1 verifier fails closed instead of guessing. |
| `fail-22-float-in-event` | MUST FAIL | A float inside an event: not representable in the canonical form, rejected at parse time. |
| `fail-23-duplicate-json-key` | MUST FAIL | A JSON object with a duplicated key (parsers disagree on which wins): rejected. |
| `fail-24-first-entry-not-chain-open` | MUST FAIL | Chain does not begin with chain_open. |
| `fail-25-inclusion-proof-tampered` | MUST FAIL | One byte of the audit path changed. |
| `fail-26-inclusion-proof-wrong-index` | MUST FAIL | Proof for entry 3 claims to be for index 2. |
| `fail-27-inclusion-proof-entry-altered` | MUST FAIL | The disclosed entry content was edited after the proof was made. |
| `fail-28-inclusion-proof-wrong-tree-size` | MUST FAIL | Proof generated for a 4-entry tree presented against the 5-entry checkpoint. |
| `fail-29-ots-wrong-digest` | MUST FAIL | OpenTimestamps file stamps a different digest than the checkpoint. |
| `fail-30-ots-not-an-ots-file` | MUST FAIL | A file that is not an OpenTimestamps proof. |
| `fail-31-chain-id-changed-in-genesis` | MUST FAIL | chain_id edited in entry 0: its hash, every later chain_id and the checkpoint origin all disagree. |
| `fail-32-approval-expiry-stripped` | MUST FAIL | expires_at removed from a signed approval so a late execution passes the gate; the approver signature covers expires_at, so it no longer verifies. |
| `fail-33-approval-method-altered` | MUST FAIL | The recorded approval method is changed after signing; the signature covers it. |
| `fail-34-approval-replayed-after-rejection` | MUST FAIL | approved(ap-1), rejected(ap-2), then a literal copy of the signed ap-1 and an execution. approval_id must be unique in a chain. |
| `fail-35-one-approval-two-executions` | MUST FAIL | One approval, two executions of the same request. An approval authorises exactly one attempt. |
| `fail-36-failed-attempt-without-approval` | MUST FAIL | phase=failed may mean partial execution, so it is gated like executed: no approval, fail. |
| `fail-37-trailing-newline-in-chain-id` | MUST FAIL | chain_id carries a trailing newline escape ("...\n"); hex fields are exactly 64 characters. |
| `fail-38-expires-at-not-a-date` | MUST FAIL | expires_at matches the pattern but is not a real time (month 99): it would never expire. |
| `fail-39-seq-beyond-safe-integer` | MUST FAIL | seq above 2**53-1: a format failure (exit 1), not a usage error. |
| `fail-40-deep-nesting` | MUST FAIL | An event nested 100 levels deep (limit: 64 per entry). Rejected cleanly, without a crash. |
| `fail-41-crlf-line-endings` | MUST FAIL | CRLF line endings. Lines end with \n only. |
| `fail-42-missing-final-newline` | MUST FAIL | The last line has no terminating newline (an interrupted write looks like this). |
| `fail-43-small-order-approver-key` | MUST FAIL | The approval is "signed" with the identity point as public key, which satisfies the equation for any message. Small-order keys are rejected. |
| `fail-44-inclusion-proof-version-not-integer` | MUST FAIL | The proof declares "v": true. Only the integer 1 is accepted. |
| `fail-45-checkpoint-size-out-of-range` | MUST FAIL | A signed checkpoint whose size has 40 digits (above 2**53-1): the checkpoint is rejected as malformed (exit 1, not a usage error). |
| `fail-46-deny-lifted-by-allow` | MUST FAIL | deny, then a later policy 'allow', then executed (no approval required). A later decision does not lift a deny; only a later human approval does. |
| `fail-47-approved-then-deny-then-allow` | MUST FAIL | approved, then deny, then allow, then executed (approval required). The approval predates the deny, and the allow does not lift it. |
| `fail-48-deny-approved-then-rejected` | MUST FAIL | deny, approved, rejected, executed (no approval required). The latest human approval after the deny is 'rejected', so the deny stands. |
| `fail-49-inclusion-proof-entry-extra-member` | MUST FAIL | The disclosed entry hashes correctly but carries an extra top-level member that the entry hash does not cover. It is rejected instead of being reported as matched. |
| `fail-50-checkpoint-too-many-signature-lines` | MUST FAIL | A checkpoint with 17 copies of a valid signature line (the limit is 16). Rejected as malformed before any signature is verified. |
| `pass-01-approval-flow-full` | MUST PASS | Signed approval flow; checkpoint signed by the trusted key; approver key pinned. Every layer except timestamp/inclusion is ok. |
| `pass-02-minimal-low-risk` | MUST PASS | Smallest useful chain: open, request, executed. No approvals involved. |
| `pass-03-no-checkpoint` | MUST PASS | Log alone. Passes, but checkpoint layers are not_checked: truncation or full rewrite would NOT be detected. |
| `pass-04-unsigned-tail` | MUST PASS | Checkpoint covers the first 3 of 5 entries; the 2 trailing entries are unsigned and reported as such. |
| `pass-05-no-trusted-key` | MUST PASS | Checkpoint supplied but no --vkey: root checked, signature not_checked (a key shipped with the log must not be trusted). |
| `pass-06-unpinned-approver` | MUST PASS | Approval signatures verify under the embedded key but no approver key is pinned: identity binding is NOT established (not_checked). |
| `pass-07-cross-verification` | MUST PASS | A cross_verification event: author from provider-a, reviewers from provider-b (disagree) and provider-a (agree). |
| `pass-08-unicode-canonical-form` | MUST PASS | Non-ASCII strings and keys whose UTF-16 order differs from code-point order (RFC 8785 ordering). |
| `pass-09-ots-digest-binds` | MUST PASS | Synthetic pending OpenTimestamps file whose digest equals SHA-256 of the checkpoint text. Binding is checked; Bitcoin attestation is NOT (unavailable). |
| `pass-10-inclusion-proof-only` | MUST PASS | Selective disclosure: only entry 3, its inclusion proof and the signed checkpoint. No other entry is revealed. |
| `pass-11-inclusion-proof-with-log` | MUST PASS | Inclusion proof checked alongside the full log. |
| `pass-12-limit-full-rewrite-no-checkpoint` | MUST PASS | LIMIT: a host-level attacker rewrites and re-chains the whole log. With no external checkpoint nothing detects it. Passes with checkpoint layers not_checked. |
| `pass-13-limit-truncation-no-checkpoint` | MUST PASS | LIMIT: dropping the last entries leaves a valid shorter chain. Without an external checkpoint this is undetectable. |
| `pass-14-extension-event` | MUST PASS | Event types prefixed 'x-' are opaque extensions: hashed and chained, not interpreted. |
| `pass-15-inclusion-proof-untrusted-checkpoint` | MUST PASS | A correct audit path, but no trusted --vkey: the checkpoint size and root are unauthenticated, so inclusion_proof is not_checked (never ok). |
| `pass-16-fresh-approval-per-attempt` | MUST PASS | A failed attempt consumes its approval; the retry runs under a second, separately signed approval. |
| `pass-17-provider-names-nfc-ascii-case` | MUST PASS | Provider names equal after NFC and ASCII lowercasing are the same provider, so cross_provider=false is consistent. |
| `pass-18-deny-lifted-by-human-approval` | MUST PASS | deny, allow, then a signed human approval, then executed (no approval required). The human approval after the deny lifts it; approval_gate is ok because the deny rule was evaluated. |
| `pass-19-deny-after-approval-reapproved` | MUST PASS | approved, deny, a second signed approval, executed (approval required). The second approval lifts the deny and authorises the one attempt. |
